# Wireless Gateway — API

Устройство на ESP32: шлюз между Wi-Fi и приборами на RS-485 (Modbus RTU),
плюс конфигурация, файловая система и прошивка по воздуху.

## Протокол

Транспорт — WebSocket, порт `CONFIG_WEB_SOCKET_SERVER_PORT` (81), путь `/api`.
Клиент шлёт JSON-объект, сервер отвечает JSON-объектом.

```json
{"FID":"uart2.modbus","FLAGS":0,"SID":7,"ARG":{"ADR":1,"FN":3,"RA":800,"RVC":3,"AWT":600}}
```

| Поле | Обязательно | Смысл |
|---|---|---|
| `FID` | да | имя сервиса, `<подсистема>.<действие>` (например `uart2.modbus`). Числовых кодов больше нет: числовой FID отклоняется |
| `FLAGS` | да | `0` — одноразовый запрос; `4` — долгоживущая подписка; бит `8` — снять вызов |
| `SID` | нет | назначает КЛИЕНТ, чтобы отличить свой ответ; сервер только повторяет его. Нет `SID` — нет поля в ответе |
| `ARG` | нет | аргументы сервиса, объект |

Ответ приходит в двух частях: сначала подтверждение приёма
`{"FID":"uart2.modbus","SID":"0x00000007","ARG":{"STA":"0x00000005"}}`
(`STA` — статус, `0x5` = DELIVERED), затем сам результат от обработчика.
Успешный результат тоже содержит `STA` (`0x0` = OK), ошибки — `ERR` и `MSG`.

### Подписки

`FLAGS:4` — вызов живёт, пока клиент не снимет его (`FLAGS` с битом `8`) или не
оборвёт соединение. Повтор запроса регулируется полем `ARG.RDL` (мс): без него
запрос повторяется сразу, как только освободится исполнитель.

## Сервисы

| FID | Назначение |
|---|---|
| `echo` | проверка связи |
| `sys.info` | состояние: MAC/IP, клиенты AP, память, файловая система |
| `sys.files` | листинг каталога файловой системы: `ARG` = `{"PATH":"/maps"}`, ответ — `PATH`, `PARENT` и массив `FILES` (`NAME`, `SIZE`, `DIR`) |
| `sys.file.write` | запись файла порциями: `ARG` = `{"PATH":"/maps/x.jsonc","OFFSET":0,"DATA":"<base64>","LAST":0}`, ответ — `{"STA":"0x00000000","WRITTEN":<байт принято>}`. `OFFSET` 0 начинает файл заново, `LAST` 1 завершает; данные идут порциями по ~6 КБ (предел сообщения транспорта — 16 КБ). Файл пишется во временный `.<имя>.part` и встаёт на место цели только на `LAST` |
| `sys.file.delete` | удаление файла: `ARG` = `{"PATH":"/maps/x.jsonc"}` |
| `sys.file.rename` | переименование: `ARG` = `{"FROM":"/maps/x.jsonc","TO":"/maps/y.jsonc"}` (`TO` — полный путь либо имя в каталоге `FROM`); на существующее имя — отказ (`ERR` = `EXIST`) |
| `wifi.sta` | параметры подключения к внешней точке доступа |
| `wifi.ap` | параметры собственной точки доступа |
| `sys.net` | настройки IPv4 интерфейсов (DHCP или статические) |
| `sys.reboot` | перезагрузка шлюза |
| `sys.fw.begin` | начать обновление прошивки: `ARG` = `{"SIZE":<байт>}`, ответ — `{"STA":"0x00000000","SESSION":1}`; свободный OTA-раздел стирается под заявленный размер |
| `sys.fw.write` | порция образа: `ARG` = `{"SEQ":<номер порции>,"DATA":"<base64>"}`, ответ — `{"STA":"0x00000000","WRITTEN":<байт принято>}`. `SEQ` — строго следующий номер (первая порция — 1), данные идут по 8 КБ (предел сообщения транспорта — 16 КБ). Пока заливка идёт, вызов остаётся открытым: этим служба замечает, что порции перестали приходить |
| `sys.fw.end` | проверить и включить образ: `ARG` = `{}` или `{"MD5":"<32 hex>"}` (MD5 самого образа, необязателен), ответ — `{"STA":"0x00000000","OK":1,"REBOOT":1}`; устройство перезагружается в новый раздел |
| `sys.fw.abort` | отказаться от заливки: `ARG` = `{}`, ответ — `{"STA":"0x00000000","OK":1}`; сессия OTA освобождается, прежняя прошивка остаётся рабочей |
| `uart1.config` / `uart2.config` | настройки порта: скорость, биты, чётность, стопы |
| `uart1.rx` / `uart2.rx` | приём сырых данных порта |
| `uart1.tx` / `uart2.tx` | передача сырых данных (base64) |
| `uart1.echo` / `uart2.echo` | эхо порта вкл/выкл |
| `uart1.modbus` / `uart2.modbus` | запрос к прибору по Modbus RTU (наш RS-485 — `uart2.modbus`) |

Пример запроса к прибору: `ARG` = `{"ADR":1,"FN":3,"RA":800,"RVC":3,"AWT":600}`,
ответ — `{"ADR":1,"FN":3,"CV":0,"RA":800,"RC":3,"ERR":0,"RD":[2910,0,0]}`.
`ERR` в этом ответе — код исключения Modbus из кадра прибора (или код отказа
каркаса: 1 память, 2 аргументы, 3 старт, 4 прибор не ответил, 5 линия занята).

## Сервисы по интерфейсам

Ядер API в прошивке два — по одному на транспорт: точка доступа (AP) и станция
(STA). При установлении соединения транспорт определяет интерфейс по локальному
адресу сокета и передаёт соединение экземпляру своего интерфейса, а тот — своему
ядру. Поэтому маски интерфейсов в ядре нет: сервис оказывается тому, на чьём ядре
он зарегистрирован. Один и тот же метод регистрируется на обоих ядрах с разными
контекстами — так обработчик понимает, откуда его вызвали (например, менять
настройки можно только из точки доступа, а со станции — только читать).

Веб-слой разделён на две части. Сокетный слой (`main/web_httpd.c`) — httpd на
порт: страницы и файлы на `CONFIG_WEB_SERVER_PORT`, WebSocket на
`CONFIG_WEB_SOCKET_SERVER_PORT`; привязать httpd к интерфейсу нельзя, поэтому
порт лишь принимает соединение и передаёт запрос объекту веб-сервера того
интерфейса, с которого пришло соединение. Объект веб-сервера
(`main/web_server.c`) — на каждый интерфейс: своя таблица зарегистрированных
путей с обработчиками, своя политика доступа и учёт сессий; он и решает, что
этому интерфейсу оказано. Таблица «путь → интерфейсы» — по-прежнему
`main/web_iface_policy.c`, но исключений «только точка доступа» в ней больше нет:
прошивку, последнее такое правило (`POST /update`), принимает служба ядра API
(`sys.fw.*`), зарегистрированная только на AP-ядре. Маршрута `/update` не
существует ни в одном объекте веб-сервера, поэтому по HTTP на этот путь
отвечает 404.
Транспорт не поднимает своего httpd: при открытии он регистрирует WS-точку `/api`
в объекте своего интерфейса, и веб-сервер отдаёт ему соединение и кадры.
Вшитая страница конфигурации (`/config`, `/config.html`) зарегистрирована только
в объекте точки доступа; на станции этих путей нет, и запрос по ним — обычный
путь файловой системы (нет файла — 404). Файловый менеджер HTTP-методов не имеет
вовсе: листинг, запись, удаление и переименование файлов идут по WebSocket
(`sys.files`, `sys.file.*`) и есть на обоих ядрах. По HTTP GET файлы
по-прежнему отдаются (карты `regmaps/*`, страницы из LittleFS) — так браузер их
и получает.

Ядро не заводит ни задач, ни очередей, ни задержек: такт ему даёт приложение —
одна задача `api_worker_task` в `main/app.c` по очереди зовёт `api_worker()` для
обоих ядер. От системы ядру нужны РОВНО три вещи — мьютекс, чтение таймера и
журнал, — и каждая принимает системный контекст: они приходят таблицей
`api_system_t`, которую приложение собирает из `platform.h` и передаёт в
`api_init()` рядом с объектом транспорта. Запрос сервису доставляется вызовом
его обработчика (вернул TRUE — получит вызов снова на следующем такте, вернул
FALSE — вызов завершён), а ответ уходит по дескриптору вызова
(`api_reply`); несрочные данные сервис рассылает подписчикам имени
(`api_broadcast`). Обработчик получает дескриптор ядра, на котором
зарегистрирован, первым аргументом.

## Где что лежит

| Каталог | Что там |
|---|---|
| `api/` | ядро API: вызовы, подписки, регистрация сервисов (`api_register_handler`), такт (`api_worker`) и ответ клиенту (`api_reply`, `api_broadcast`). Платформу не знает: мьютекс, время и журнал приходят таблицей `api_system_t` |
| `platform/` | платформа приложения и сервисов: мьютексы, очереди, время, задачи, журнал (`platform.h`). Ядро API её не включает |
| `transport/` | контракт транспорта (события и операции). О ядре API не знает ничего |
| `main/ws_transport.c` | транспорт на WebSocket: экземпляр порождает веб-сервер интерфейса (`web_server_open_websocket`), экземпляр помнит свой веб-сервер и URI, активирует точку по `open` |
| `main/web_httpd.c` | сокетный слой веб-сервера: httpd на порт, сессии, TCP_NODELAY, бюджеты отправки, развод запросов по интерфейсу |
| `main/web_server.c` | объект веб-сервера на интерфейс: таблица путей, политика доступа, учёт сессий, порождение транспорта интерфейса |
| `main/apih_*.c` | сервисы: системные, UART, Modbus |
| `main/web_file_server.c` | отдача файлов и страниц по HTTP |
| `main/apih_fw.c` | обновление прошивки по API (`sys.fw.begin/write/end/abort`), только AP-ядро |
| `main/flash_data/` | веб-страницы и карты регистров (образ LittleFS) |
| `CodeLibrary/CL` | сабмодуль с контейнерами и протоколами (Modbus, base64, JSON-утилиты) |
| `json/` | разбор JSON без выделения памяти (jsmn) и запись ответов |
| `tests/unit/` | хостовые тесты (CppUTest, ASan/UBSan/LSan) |

## Сборка и проверки

```sh
. /home/dmitry/.espressif/tools/activate_idf_v6.0.1.sh ; idf.py build
idf.py -p /dev/ttyUSB0 flash monitor
make -C tests/unit && tests/unit/build/test_runner
```

Тесты собираются хостовым компилятором, поэтому `make` запускать в шелле БЕЗ
активации IDF (иначе подхватится xtensa-тулчейн).
