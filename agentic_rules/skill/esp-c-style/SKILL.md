# Стиль C-кода: Linux kernel rules, адаптированные под ESP-IDF

База — kernel coding style (https://www.kernel.org/doc/html/latest/process/coding-style.html).
Адаптации под этот проект перечислены явно; всё остальное — как в ядре Linux.

## Когда применяются правила

- **Новый файл или модуль** — применяй все правила ниже целиком.
- **Правка существующего файла** — сохраняй стиль файла вокруг правки (в т.ч. если он отступает от правил). Не переформатируй файл мимоходом и не «чини» чужой стиль в том же изменении: форматирование — отдельная задача, как и в kernel coding-style.
- Формат-фиксы не смешивай с логическими изменениями в одном коммите.

## Отступы и длина строки

- Отступ **4 пробела, без табов**. (Адаптация: в ядре — табы по 8; принцип тот же — крупный отступ рано сигналит о перевложенности, но ESP-IDF принял 4 пробела, и весь код проекта так написан.)
- Больше 3 уровней вложенности — сигнал вынести код в отдельную функцию.
- Длина строки — **предпочтительно 80 колонок**. Если перенос сильно ухудшает читаемость, длиннее допустимо, но не прячь за лимитом информацию.
- **Не разрывай** user-visible строки (логи, сообщения об ошибках) — их ищут grep'ом по тексту.
- Нет trailing whitespace; пустые строки не должны содержать пробелов.
- Несколько операторов на одной строке — нельзя; запятыми скобки не заменять (`do_this(), do_that();` — запрещено).

## Скобки

- Открывающая `{` — в конце строки для **всех** блоков, включая функции:

```c
void net_init(app_context_t *app) {
    ...
}
```

(Адаптация: в ядре скобка функции — на новой строке; ESP-IDF-конвенция и весь код проекта — как выше.)

- Одиночный оператор — без скобок:

```c
if (condition)
    action();
```

- Несколько операторов или «смешанные» ветки (в одной есть блок, в другой нет) — скобки во всех ветках:

```c
if (condition) {
    do_this();
    do_that();
} else {
    otherwise();
}
```

- `case` выравнивать на уровень `switch` (без двойного отступа).
- `do { } while (cond);` и `} else {` — закрывающая скобка на одной строке с продолжением.

## Пробелы

- Пробел **после** ключевых слов `if, switch, case, for, do, while`; **без** пробела после `sizeof, typeof, alignof, __attribute__`.
- Без пробелов внутри скобок: `sizeof(x)`, не `sizeof( x )`.
- `*` прижимается к имени переменной/функции, не к типу: `char *buf;`, `uint8_t *parse(const char *s);`
- Пробел с обеих сторон у бинарных операторов `= + - < > * / % | & ^ <= >= == != ? :`; **нет** пробела после унарных `& * + - ~ !`; нет пробела вокруг `.` и `->`; нет пробела между префиксным `++/--` и операндом и перед постфиксным.

## Именование

- Глобальные функции и переменные — описательные: `net_apply_config`, не `nac`. Глобальное имя `foo` — убийственный грех.
- Локальные — короткие: `i`, `j`, `tmp`, `ret`. `loop_counter` не нужен, если смысл очевиден.
- Без венгерской нотации — тип известен компилятору.
- **`_t`-typedef'ы разрешены** (адаптация: в ядре typedef почти запрещён, но в ESP-IDF так оформлены все структуры, и проект этой конвенции следует). При этом typedef'ы указателей — не плодить.
- Запрещены термины master/slave → primary/replica, initiator/target, controller/device; blacklist/whitelist → denylist/allowlist, blocklist/passlist.
- Возврат: функция-**предикат** (имя — вопрос/утверждение) возвращает `bool` (`0` = нет, ненулевое = да); функция-**действие** (императив) возвращает код ошибки: в ESP-IDF это `esp_err_t`/int, где `ESP_OK`/`0` = успех, отрицательное = ошибка. Не смешивать две конвенции — это источник трудноуловимых багов.

## Функции

- Короткие, делают одно дело; ≤ 5–10 локальных переменных. Больше — дробить на helper-функции с описательными именами.
- **Все локальные переменные объявляются в начале функции, до исполняемого кода**: сначала блок объявлений, потом код. Объявления по мере надобности внутри тела не допускаются; счётчики циклов тоже выносятся наверх (`i` объявлен выше, `for (i = 0; ...)`).
- Между функциями — одна пустая строка.
- В прототипах указывай имена параметров (информация для читателя), не используй `extern` для функций.

## Централизованный выход

- Если функция выходит из нескольких мест с общей очисткой — `goto` с **осмысленной** меткой: `out_free_buf:`, `err_free_bar:` + `err_free_foo:`. Не `err1:`/`err2:` — их придётся перенумеровывать, и корректность трудно проверять.
- Очистки нет — просто `return` сразу.
- Помни о «one-err» баге: метка не должна освобождать то, что на этом пути ещё не выделено; дели на отдельные метки.

## Комментарии

- Комментируй **ЧТО** и **ПОЧЕМУ**, не КАК. Внутри тела функции — только короткие предупреждения о неочевидном; иначе вынеси код в функцию с именем.
- Многострочный стиль:

```c
/*
 * Текст комментария
 * следующими строками.
 */
```

- Одно объявление на строку — остаётся место для комментария к каждому полю.
- Комментарии в этом проекте пишутся по-русски (см. `main/connection.c`) — сохраняй язык файла.

## Макросы

- Константы и enum-значения — ЗАГЛАВНЫМИ: `#define CONSTANT 0x12345`.
- Несколько операторов — только `do { } while (0)`.
- `static inline`-функции предпочтительнее function-like макросов (side effects, unused variables, документирование).
- Скобки вокруг выражений и параметров: `#define CONSTEXP (CONSTANT | 3)`.
- Запрещено: макросы, меняющие поток управления вызывающего кода; макросы, зависящие от «магического» имени локальной переменной; макросы-аргументы как l-values; локальные переменные внутри макросов с распространёнными именами (`ret` → `__foo_ret`).

## Условная компиляция

- Минимум `#if/#ifdef` в `.c`-файлах: выноси в заголовок функции с no-op заглушками в `#else` и вызывай безусловно.
- Нетривиальные блоки (больше пары строк) — комментарий после `#endif`: `#endif /* CONFIG_X */`.
- Символы конфигурации проекта — `CONFIG_*` из sdkconfig/Kconfig.projbuild.

## Логи

- Макросы `ESP_LOGx` через модуль проекта `gw_log.h` с `#define GW_LOG_MODULE GW_LOG_*` — как в `main/connection.c`.
- Сообщения краткие и однозначные, **без точки в конце**; числа в скобках `(%d)` ценности не добавляют — не печатать.
- Штатная работа должна быть тихой: отладочное — на debug-уровне.
- Строки логов не разрывать (grep).

## bool

- Для флагов — `bool` (`<stdbool.h>`), значения `true`/`false`, не `1`/`0`; конструкция `!!` при `bool` не нужна.
- Не использовать `bool` там, где важен размер/выравнивание (битовые поля, структуры на стыке с драйвером) — там `u8`/битовое поле.

## clang-format

- Для автоматики используй конфиг из `references/clang-format.md` (адаптация `.clang-format` ядра Linux). Для нового файла: `clang-format -i file.c`, для патча — `git clang-format`.
- НЕ вставляй `// clang-format off/on` в исходники проекта.
- Памятка: clang-format ломает выравнивание однострочных `#define` и designated initializers (см. references) — такие места после прогона проверяй глазами.

## Проверка перед коммитом

- `git diff --check` (trailing whitespace/conflict markers).
- Стиль нового кода прогоняй через clang-format (см. выше).
- Тесты: юниты `tests/unit/` (CppUTest) и сценарии `tests/fuzz/`; сборка — `idf.py build`. Правила из CLAUDE.md: изменение + тесты в одном коммите.

## Контекст проекта (не заменяет, а дополняет)

- Архитектура: `docs/architecture_rules.md` (Clean Architecture для embedded: зависимости внутрь, HAL/OSAL, `app.c` — единственная точка связывания). Форматирование не отменяет эти ограничения.
- Если вопрос не про стиль, а про структуру/дизайн — см. правила архитектуры, а не этот скилл.
